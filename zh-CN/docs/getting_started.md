# EGM 安装与工作流指南

## 背景

**大象-金鱼模型 (EGM)** 是基于 Dave Rensin 奠基性文章 [Elephants, Goldfish, and the New Golden Age of Software Engineering](https://medium.com/@drensin/elephants-goldfish-and-the-new-golden-age-of-software-engineering-c33641a48874) 的一套规格驱动开发 (SDD) 实现方案。

一般建议：在深入使用工具之前，先理解核心哲学。亲身走完一两遍对话流程（尤其是如果你还不熟悉 LLM 的话），会让你直观感受到 LLM 的各种特性，并培养驾驭它们的直觉。

即便你不对 EGM 做任何其他尝试，也建议先这样跑几次，看看能否从 LLM 那里获得比以往更高质量的回复。除了你的时间之外，它完全免费，无需安装任何工具，而且所有步骤都按 1 到 N 清晰编号。

如果你喜欢这种做法带来的效果，很快就会注意到一些现象：你会厌倦一遍遍复制粘贴提示词；你会发现某些重复性操作，并希望 LLM 能自己搞定第 1 步到第 X 步。EGM 框架正是由此诞生。一群实践了一段时间的开发者总结出了一些共通模式，并试图用更少的步骤让大家更容易上手。

## 运行时环境配置

EGM 的技能与专家角色被打包为适用于 **Antigravity**、**Claude Code**、**Claude Cowork**、**OpenAI Codex** 和 **ChatGPT Work** 的插件（安装说明请参阅[宿主环境](harnesses.md)）。

1.  **技能（Skills）**：`skills/` 目录下的技能可通过插件/扩展清单（manifest）安装。本指南以不带前缀的形式展示命令（例如 `/egm-brainstorm`、`/egm-draft`、`/egm-review`）；关于如何在 Antigravity（agy CLI）、Claude Code 和 Codex 中调用这些命令（例如使用 `/egm:` 前缀），请参阅[尝试你的第一个设计](../README.md#try-your-first-design)。
2.  **专家角色（Personas）**：`agents/` 目录下的提示词为子智能体定义了相互隔离的系统指令。

## 主工作流

虽然 EGM 有一套“主工作流”，但该流程并非僵化的教条。各个技能被设计为可以灵活组合。如果符合你的实际需求，你完全可以——也应该——按不同顺序调用它们。

总体目标是同时拥有：

*   符合你预期的代码
*   解释“为什么代码以这种方式存在”的文档

你可能会发现自己在多个技能之间来回切换以解决眼前的问题，这正是我们所鼓励的。如果你认为一个简单的 Bug 修复可以一次性直接搞定，就不要强行套用设计优先流程。因地制宜，选择最趁手的工具。

哪个技能能解决你当前的瓶颈，就用哪一个。

### 核心循环

“核心”工作流如下所示：

1.  **`/egm-brainstorm`**：启动上游构思会话。该命令引导开发者澄清概念，随后派生一个多视角的金鱼蜂群对该概念进行压力测试，并生成结构化的 `concepts_brief.md` 产物。

2.  **`/egm-draft`**：起草设计文档。该命令将概念简报或初步想法转化为 `docs/designs/` 目录下逐节编写的正式 Markdown 设计文档。

3.  **`/egm-review`**：使用**金鱼**评审设计。在全新、零上下文的会话中对设计文档执行多阶段评审，验证其完备性、清晰度、自包含性与实现就绪程度。

    这一步在设计上就会给出*大量*反馈。采纳你认为有价值的意见，忽略其余部分即可。

4.  **人类评审**：通过 Pull Request 将你的设计发送给另一位人类同事评审。EGM 并不取代人类监督，反而鼓励人类介入。人类评审对于确保长期的产品一致性与优先级排序至关重要。

5.  **实现**：让 AI 按照计划进行构建。实现指引应当已经写在你的设计文档中。如果 LLM 犯了小错误，你可以自己随手修正，或让 LLM 做定点修复；如果偏离太远，则更新设计文档并重新尝试。

    > 注意：每个团队在实现阶段都有各自关注的不同技能，例如代码可读性与风格指南、性能分析工具、测试策略等。EGM 在此不做强行约束。请把你们团队的技能加入到实现计划中！

## 漂移检测

为确保设计规格与现行代码库随时间演进始终保持同步，EGM 提供了漂移检测技能：

*   **`/egm-drift-report`**：扫描你的设计目录及其引用的代码，检测是否存在漂移。一旦发现任何偏离，都应进行调和——要么更新文档，要么修改代码，由人类决定选择哪一种。

我们建议每周运行一次。如果你的团队有定期维护轮值制度，将其纳入每周例行仪式会非常有效。

## 存量代码库引导初始化（Bootstrapping）

### 目录结构

我们建议 EGM 项目目录采用类似如下的结构：

```text
path/to/project
├── _agents/                   # （可选，但推荐）
│   └── skills
│       └── <project>_elephant # 用于加载项目上下文的自定义技能
│           └── SKILL.md
└── docs/
    └── designs/               # EGM 设计文档目录
        ├── SITEMAP.md         # 设计产物的索引
        └── FEATURE.md         # 详细的设计规格文档
```

### 引导初始化

`/egm-bootstrap <path/to/project>` 会在目录树中自动生成、格式化并对各层 README 执行首轮校验，以建立代码库上下文。人类仍应对其产出进行评审。它通过自底向上的递归汇总流程来实现：

1.  **叶子目录**：为每个叶子目录生成一份 `README.md`，说明该目录的用途并记录每个文件的功能。

2.  **父目录**：沿目录树向上递归，通过汇总子目录的 README 来生成父目录的 `README.md` 文件。

3.  **根目录**：汇总生成根目录的 `README.md`，提供完整的高层系统架构地图。

这种结构化的上下文层级让大象能够更轻松地导航代码库。EGM 倾向于让人类掌控这些输出，这正是该技能存在的意义。如果你的设计产物已经覆盖并引用了全部代码，那么这些 README 也许并非必需。

### 项目上下文技能（可选）

你可以专门为自己的项目创建一个自定义的 `<project>-elephant` 技能。这个技能无需复杂：只需向 LLM 介绍你的项目，并提供你认为最相关的上下文链接即可。仅此而已。

该技能可以非常方便地为 LLM 快速提供代码路径、文档和重要设计资料的引用。

随着代码库不断增长、更多设计文档归档沉淀，这个上下文加载器能让大象检索相关的架构演进历史，从而支撑更有深度的设计讨论与更精准的功能实现。
