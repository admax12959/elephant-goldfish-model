# 多宿主环境支持：Hermes Agent、OpenClaw 与 Delta

* **作者：** Sriram ([@Seburan](https://github.com/Seburan))、Sriram Yatham ([@yathamsriram243-blip](https://github.com/yathamsriram243-blip))
* **状态：** 阶段 1 设计提案；原生契约与真实运行尚未验证
* **更新日期：** 2026-10-30
* **关联 Issue：** [#116](https://github.com/google/elephant-goldfish-model/issues/116)

## 1. 问题与目标

大象-金鱼模型 (EGM) 在不同宿主环境之间共享其技能、智能体人格与文档标准。新增任何宿主都必须完整保留这份共享文本，以及起草与金鱼评审之间的新鲜上下文边界。

本提案定义了接入 Hermes Agent、OpenClaw 与 Delta 的技术要求，并不代表其中任何一项已具备可用支持。

目标：

* 复用权威的 `skills/`、`agents/` 与 `resources/` 内容。
* 为每个特定宿主版本选定有文档依据的安装格式。
* 验证不继承父会话对话的原生子智能体委派能力。
* 通过宿主级权限控制强制执行评审员只读访问。
* 在宣称支持前，要求提供完整的安装与工作流验证证据。

非目标：

* 分叉（fork）技能文本，或引入运行时翻译服务。
* 新增聊天桥接器、注册中心或设备同步机制。
* 在阶段 1 交付猜测性的清单文件或未经测试的安装命令。
* 仅凭离线元数据测试就宣称支持。

## 2. 海尔迈耶教义问答评估

| 问题 | 评估 |
| --- | --- |
| 我们试图做什么？ | 在保持共享提示词与独立评审的前提下，让 EGM 运行于三个新增宿主环境之上。 |
| 目前是如何做的？ | [宿主环境指南](../harnesses.md) 记录了现有集成；本提案涉及的三个集成目前均未附带经验证的原生运行记录。 |
| 创新点是什么？ | 尽可能复用兼容产物包，仅在固定宿主版本确有需要时添加轻薄宿主适配器。 |
| 谁将受益？ | 目标宿主的用户，以及原本不得不维护多份提示词副本的维护者。 |
| 有哪些风险？ | 不受支持的发现路径、继承项目上下文、可写评审员，以及过早宣称支持。 |
| 成本是多少？ | 贡献者时间与真实探针的模型消耗；运行耗时与 Token 成本尚未实测。 |
| 需要多长时间？ | 各宿主在其契约验证完成后独立推进，不承诺固定交付日期。 |
| 验收考题是什么？ | 阶段 1 定义验收门禁；阶段 2 为每个宿主提供 Schema、安装、隔离性、权限与工作流验证证据。 |

## 3. 宿主契约与待决问题

以下仅为调研输入，而非经过测试的 EGM 集成。在将输入转化为实现契约前，必须先记录宿主版本号及对应的文档或源码修订版。

| 宿主环境 | 文档化输入 | 尚待验证的契约 |
| --- | --- | --- |
| Hermes Agent | 当前[委派文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)暴露了 `delegate_task(goal, context)`。子会话拥有新鲜对话，但继承工具访问权限且可能接收工作区项目上下文。 | 包发现机制、精确安装版本、智能体人格加载、项目上下文抑制以及强制只读权限。不要假设存在 `hermes.spawn` 或类似 Claude 的按次工具过滤器。 |
| OpenClaw | [清单文档](https://docs.openclaw.ai/plugins/manifest) 区分了原生 `openclaw.plugin.json` 插件与兼容产物包。 | 先探测现有 EGM 产物包；若不兼容，再文档化原生 Schema 与包根目录。针对固定版本验证 `openclaw plugins install`、已加载插件身份以及精确的 `sessions_spawn` Schema。仅重命名 JSON 文件不能证明兼容。 |
| Delta | [#116](https://github.com/google/elephant-goldfish-model/issues/116) 将 Delta 列为目标宿主。 | 确认产品实体、上游仓库、发行版、安装格式与委派 API。此处不预先指定 `delta.spawn`、隔离标志、清单路径或最低版本。 |

在对应源码与原生安装探针证实之前，不选定任何宿主专属清单路径或最低引擎版本。具名智能体人格发现与嵌套委派同样未经验证。

## 4. 架构与评审边界

现有根目录 `plugin.json` 保持为权威元数据来源。若现有兼容产物包能够保留全部运行时资源，则优先直接复用。若确需适配器，将宿主专属字段保存在该适配器中，从权威清单拷贝共享元数据，并针对该宿主 Schema 支持的字段测试精确一致性。

每名评审员接收其智能体人格、目标文档与所需资源，绝不转发父会话对话。同时检查提交给子智能体的提示词与宿主注入的上下文；仅凭新鲜对话本身不足以证明排除了项目指令或记忆。

评审员必须无法修改文件或执行具备变更能力的工具。应以宿主强制执行的权限控制而非提示词指令作为证明。Claude 的 `Read`、`Grep` 与 `Glob` 只是一个宿主专属示例；其他宿主必须将相同的“禁止变更”要求映射到自身经过验证的控制机制，不得假定字面相同的工具名或通用的 `tools` 参数。

若某个宿主无法满足隔离或权限要求，其金鱼评审集成保持“不支持”状态——应直接中止评审，绝不在父上下文中或以更宽泛的权限运行。

## 5. 备选方案

| 选项 | 决策 |
| --- | --- |
| 复用现有兼容产物包 | 当原生安装探针证实支持发现与资源访问时优先选用，可避免重复元数据。 |
| 轻薄原生适配器 | 仅在经验证的宿主契约确有要求时使用，保持提示词内容权威唯一。 |
| 猜测性逐宿主清单 | 拒绝。合法的 JSON/YAML 语法与元数据一致性不能证明宿主接受该清单。 |
| 运行时翻译器或拷贝技能分叉 | 排除，因为会增加维护负担并引发提示词漂移。 |

## 6. 交付计划

### 阶段 1：设计

本 PR 仅包含此提案及其设计索引条目，不更改任何运行时清单、安装指南、支持记录或测试。维护者批准设计不代表认证原生宿主支持。保持 #116 开启以跟进实现与证据。

### 阶段 2：实现并验证单个宿主

实现前须获取 [AGENTS.md](../../AGENTS.md) 要求的贡献轨道审批，并基于本已合并设计提交后续 PR：

1. 明确宿主产品、精确版本、上游源码与 Schema。
2. 在新增适配器前先探测现有 EGM 产物包。
3. 实现最小必要适配器与原生委派映射。
4. 为实际 Schema、元数据与资源路径契约添加离线检查。
5. 运行原生安装、隔离性、权限与工作流探针。
6. 将证据与明确限制更新至[宿主环境指南](../harnesses.md)与[测试记录](../../TESTING.md)，仅晋升已完成测试的宿主。

在必需证据缺失期间，不得发布猜测性的安装命令或将宿主标记为“受支持”；未验证结果必须保持显式标注。

## 7. 验证与验收

阶段 1 运行 `pytest tests/unit` 与 `git diff --check`。链接测试会检查隐藏目录及其他排除路径之外的相对目标存在性与同文档锚点，不校验跨文档片段、外部 URL 或原生插件发现。

阶段 2 必须对 JSON 清单保持严格 JSON 解析，仅对要求 YAML 的格式使用 YAML 解析。应针对所选 Schema 执行真实校验，而非把元数据匹配当作 Schema 校验。

为每个宿主附上以下证据：

* 精确宿主版本与来源、EGM 提交 SHA、操作系统与模型配置。
* 干净的安装命令及显示加载了哪个 EGM 包的输出。
* 技能、智能体人格与文档标准的发现与成功读取记录。
* 原生子提示词与追踪日志，证明排除了父对话与无关项目上下文（使用仅父会话可见的金丝雀探针）。
* 实际生效的子权限配置以及证明变更尝试被阻断的负向探针（仅在提示词中要求只读是不够的）。
* 端到端的 `/egm-brainstorm`、`/egm-draft` 与 `/egm-review` 输出，并从追踪日志核实评审员完成状态、必需读取与阶段顺序。
* 已知限制、失败项与实测用量。发布前对凭证进行脱敏。

离线检查不能替代原生探针。若任一必需探针失败，保持支持状态为未验证并记录失败详情。

## 8. 回归与回滚

将验证证据固定到被测版本与 EGM 提交。后续宿主新版本不会自动继承已验证结论。若发现机制、隔离性或权限发生回归，应记录受影响版本、撤回其支持声明，并修复或回退该宿主的适配器，同时保持其他可用集成与共享提示词文本不受影响。
