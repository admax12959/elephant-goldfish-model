# 版本化运行时发布

状态：已通过合并的 #137 实现；v0.1.0 已发布。
作者：@n3wth。日期：2026-10-24。

关联 Issue：#124（已完成）。实现 PR：#137（基于已合并的 #136）。

## 问题与范围

用户需要从经过评审的提交构建出的、身份可识别的归档包。本设计用于准备包含源码身份与校验和的草稿发布（draft release），随后在正式发布前验证其精确产物。

复用[运行时打包设计](runtime_packaging.md)。不自动创建标签、不自动发布、不在 CI 中运行付费模型，也不新增宿主环境支持。

## 版本与产物契约

以根插件版本作为权威版本（canonical version）。要求 Claude 与 Codex 清单文件的版本号与之完全一致。仅接受不含前导零的 `vMAJOR.MINOR.PATCH` 标签。绝不将已发布的版本号复用于发生变更的产物。

已实现的 `scripts/prepare_release.py` 接受 `--tag`、`--commit` 和 `--output` 参数，要求提供完整的源码 SHA 以及一个新的输出目录，并产出：

- `egm-claude-VERSION.zip`
- `egm-openai-VERSION.zip`
- `SHA256SUMS`
- `RELEASE_NOTES.md`，包含源码 SHA、标签以及验证范围限制说明

本地调用仅校验传入参数并构建归档，不证明 Git 祖先关系也不运行测试。这些检查归工作流负责。本地传入的源码 SHA 只是调用方的声明，并非经过验证的源码身份。生成的发布说明中须标明这一限制。正式发布必须使用工作流在完成源码验证与精确产物检查后构建的候选包。

## 工作流与权限

从 `main` 分支手动触发（dispatch）工作流并传入一个已存在的版本标签。将标签解析为提交，并要求该提交必须是 `main` 的祖先提交。检出该提交，运行离线测试并准备归档。

构建作业（build job）拥有 `contents: read`、`id-token: write` 和 `attestations: write` 权限。构建完成后，使用按提交 SHA 固定的 `actions/attest` 为两个运行时 ZIP 签署构建来源证明（provenance）并存储到 GitHub。禁用 registry 存储记录，因此无需 registry 或 `artifact-metadata` 权限。证明签署失败会中止构建。本地准备流程不会创建来源证明。

该来源证明标识的是从 `main` 触发的工作流。其源码身份可能与作业期间检出的选定标签不同。发布说明会记录带标签的源码 SHA。正式发布前须同时核对这两个身份。来源证明仅证实产物出处，不代表宿主兼容性或代码安全性。验证时必须确认签署工作流位于 `refs/heads/main` 且与下载 ZIP 的摘要匹配，并将记录的标签 SHA 与构建作业解析出的标签提交进行比对。仅凭工作流身份不足以验证该标签映射关系。

一个独立的草稿作业（draft job）接收这些产物、验证其校验和、复核标签身份，并使用 `contents: write` 权限创建草稿发布。重复创建发布将失败且不会替换已有资产。两个作业均不创建标签，也不正式发布 Release。

## 验收与发布流程

1. 设计与实现 #136/#137 已合并，#124 已完成。
2. 首个正式发布的版本为 [v0.1.0](https://github.com/google/elephant-goldfish-model/releases/tag/v0.1.0)。
3. 针对其余宿主环境的精确产物验证在 #60 中保持开启。
4. 选定经过评审的版本与提交。在维护者创建标签前，重新生成打包内容并验证所有纳入的运行时变更。
5. 触发工作流。检查两个归档、校验和以及源码身份。使用 `gh attestation verify FILE --repo google/elephant-goldfish-model` 验证每个 ZIP，并要求签署工作流为 `main` 分支上的 `.github/workflows/release.yml`。
6. 使用这些精确产物，针对每个宣称支持的宿主环境完成 [#60 中的精确产物包验证流程](https://github.com/google/elephant-goldfish-model/issues/60)。记录已安装文件身份、宿主/模型版本、日期，以及分开记录的安装、工作流和隔离性结果。完成标准要求安装干净、产物身份符合预期，且工作流与隔离性结果达到支持标准。保留任何仅部分支持的宿主结果。
7. 评审最终发布说明并手动发布。目录上架审批与版本发布保持独立。

测试版本号不匹配、格式错误的标签与源码 ID、归档内容、校验和、覆盖拒绝以及生成物新鲜度。对工作流执行 Lint 检查，并在首次真实触发验证通过后再认定发布准备流程完成。

仅在明确说明适用性的前提下才能复用历史宿主验证证据。不得将旧候选包的结果当作新产物的通过记录。在 #105 和 #106 仍存在证据缺口期间，保持云端支持状态为“部分支持”。

## 失败处理与备选方案

失败或未通过验证的候选包应保持未发布状态。构建重试须使用全新的本地输出目录。不要替换已发布的归档或移动已有标签；应改为准备一个新的修正版本。

手工构建发布容易遗漏验证步骤或源码身份信息。自动发布则会跳过最终的证据评审环节。经过验证的草稿发布在避免重复打包构建器的同时，保留了这道最终评审防线。

本草案不代表已获维护者批准，也不宣称已经过一轮 EGM 设计评审。在发布工作流完成验证前，关联 Issue 保持开启。
