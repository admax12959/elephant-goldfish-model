# 常见问题 (FAQ)

#### 问：还有其他替代方案吗？

**答**：有，而且很多。

EGM 只是团队让 LLM 更好发挥作用的方法之一，而并非*唯一*的方法。市场上还有其他各具权衡的方案。无论你选择哪种工具，请始终牢记：*你对最终结果负责。*

#### 问：EGM 流程会产生哪些具体产物？

**答**：EGM 会产生三类核心交付物：

*   **设计文档**：经过同行评审的技术规格文档，记录设计意图、系统不变量（invariants）与战略方向。
*   **实现检查清单**：明确需要创建或修改的文件、计划进行的变更以及验证方式。
*   **增强型上下文循环**：与代码同目录存放的 Markdown 文档（例如分层 README 体系），为后续开发循环提供高质量上下文。

#### 问：在 EGM 模式下，软件工程师（SWE）会被淘汰吗？

**答**：在我们看来？不会。不过，代码生成将越来越多地委派给自动化智能体，而人类工程师的工作重心将转向把控意图，以及评审设计文档中所承载的架构决策。

#### 问：设计文档数量增加是否会造成人类评审瓶颈？

**答**：有可能。评审设计确实会增加工作量，过度的文档化也可能演变为瓶颈。我们的目标是在实现之前捕获关键问题；这最终是否能节省时间，取决于变更本身的性质以及评审的质量。

至少在现阶段，我们建议重视优先级排序。将 EGM 用在“当下最重要的事情”上，而不是事无巨细全部套用，以免压垮你的评审与发布流水线。

#### 问：这套工作流会拖慢开发者的交付速度吗？

**答**：视情况而定。设计与评审需要耗费时间，对于规模小且需求清晰的改动而言，可能并不划算。但对于存在不确定性或影响重大的变更，它们可以通过更早暴露缺失的决策来减少后期返工。

请在自己的实际任务中对比总耗时、有价值的发现以及返工成本。仅仅走完 EGM 工作流本身，并不能自动证明生产率得到了提升。

#### 问：期望设计文档完备到足以让零上下文智能体直接实现，这现实吗？

**答**：有时现实，但并非总是如此。EGM 的方法同时沉淀了战略意图与执行计划，并借助金鱼智能体提升文档质量，但 LLM 本质上仍是非确定性的。

你需要像指导一位新入职的软件工程师那样运用自己的判断力。如果它犯了小错，稍作纠正即可；如果偏离得太离谱，也许你需要回到起点修正设计文档。这是整个流程的正常组成部分，用得越多就会越得心应手。

#### 问：我应该提交大型 Pull Request 吗？

**答**：不应该。通常来说，这个问题（以及许多其他问题）的答案都是：“跟没有 AI 时代写代码时的答案一样。”
